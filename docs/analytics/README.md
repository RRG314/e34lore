# E34 Lore analytics and growth reporting

Implementation date: 8 November 2026 (UTC). Existing private repository, Site, Supabase project, community, catalog and financial ledger are retained.

## Existing measurement audit

Before this change, `UsageAnalytics` recorded an opted-in **section open**, deduplicated per section and browser tab for 30 minutes. It marked the local dedup key before the RPC returned and did not retry. These counts cannot establish page views, sessions, distinct browsers or unique people. Production held four daily/section rows and five opens on 6–7 November. They are preserved, labelled separately, and never converted into visitor history.

Commercial measurement has independent, off-by-default consent. `affiliate_clicks_daily` and `advertising_daily` contain counts, not customers or orders. `revenue_records` is the canonical financial ledger. Commission/payment source tables are not added to it a second time. Estimates, net earnings (less reversals) and receipts remain separate, as do currencies. No new ad tracker or GA4 tag was added. Counts live in Supabase and survive website deployments; local preferences live in each browser.

## Architecture and access

- `/manage/analytics` is lazy loaded in the existing management area, keyed by account and Auth revision. Every report and setting RPC checks the existing database administrator + AAL2 + verified factor + live `auth.sessions` boundary. Anonymous users, ordinary members, moderators and stale/revoked sessions cannot read reports or settings.
- New `analytics_*` tables are private, RLS enabled, and have no general table grants. No raw visitor list or individual activity view is exposed. The collector and erasure RPCs are service-role only. Public configuration returns only enabled/revision.
- The `analytics` Edge Function enforces production-origin allowlisting, a 16 KiB/time-limited JSON body, a versioned field allowlist, consent checks, bounded arrays, bot/QA filtering, known resource identities, fresh identity verification for staff exclusion, and sanitized errors. It performs its own authorization; gateway JWT verification is off because anonymous visitor collection is intentional. Provider sync requires a fresh user check plus the live administrator/MFA RPC.
- The shared contract lives in `supabase/functions/_shared/analytics-contract.mjs`. Static public resources are reproducibly generated by `node --experimental-strip-types scripts/build-analytics-registry.mjs`; `--check` verifies both browser/Edge copies. The initial registry has 646 entries. Dynamic catalog parts and drawings must exist in the canonical public catalog before their IDs/titles enter the analytics registry. New static content needs a corresponding additive registry migration. First-seen timestamps use the earliest accepted public-page observation, including delayed batches; missing-page batches cannot leave empty visitor identities.
- The browser queues at most 50 events in memory, sends up to 20 per batch, flushes periodically/on page hide, and keeps UUIDs on bounded retries. No event payload is written to local storage. IDs prevent duplicate delivery, `(page,seq)` prevents ordinal duplication, and one logical page view and one search identity are enforced in SQL. Publication prefetches do not create views.
- Raw browser UUIDs are HMACed in the service-only SQL function with a private key generated only when the owner explicitly enables collection. They have no Auth foreign key or account identity association. No raw IP, user agent, URL/query, private garage ID, VIN, image, camera matrix, stack or error message is stored.
- Public pages only are measured. Account, private garage, support, management, private workshop and configuration-archive views are excluded. Public community thread views are reduced to the community section, not member/thread IDs. Referrers are reduced server-side using the public suffix list; paths, query strings, usernames and OAuth/self referrals are discarded. Campaign codes must first be registered by an administrator.

## Metrics and their limits

A distinct browser is a random first-party identifier lasting 30 days, **not a person**. Multiple devices, resets and ID expiry can count again. New browsers are first observed in the selected range; returning browsers were observed before its start, within retained history. A browser can return within the range without entering the latter cohort. These definitions are explicit in the dashboard.

Sessions are assigned server-side across tabs: 30 minutes without accepted activity, or a four-hour maximum. Pages per session use distinct sessions with measured pages in the selected interval. Entry/exit tables are the first and last **observed pages in the range**, not guaranteed true browser entry or exit. Content filters and range boundaries can truncate sessions.

One public document keeps its page identity and sequence across guest sign-in and preference changes. The initial consent snapshot stays immutable; each batch must carry current category permission. Category availability also recognizes actual permitted events, without rewriting historical permission. A server-expired page with pending activity resumes on a new page identity, preserving event deduplication IDs and omitting the old referrer/campaign. Passive late performance callbacks alone do not create a resumed view. The 30-day identifier expiry also applies while a document remains open.

Foreground time is measured in visible, focused pages with recent interaction, capped at five minutes per page, including across preference changes. It is not proof of reading. Web Vitals use Google's `web-vitals` 6.2.3 implementation; latest per-page/metric observations avoid overweighting repeat final callbacks. LCP/INP use ms, CLS is unitless. No eligible interaction can mean absent INP. Model timing includes reference/import/GLB loading and is separate from page LCP. Client API failures are not database execution timings.

Search measurement waits for successful completion of catalog, community and public-garage requests for the exact query/context. A source failure is not recorded as a zero-result search. Thus these totals cover complete-source searches, not every keystroke or failed attempt. Technical topics retain only recognized dictionary words, up to eight distinct words, with model drawn from the public model enum. Emails, URLs, UUIDs, VIN-like strings, long numbers and unknown words are discarded. Unmatched numeric queries cannot become phone-number telemetry. Actual clicked/selected catalog identities can show requested OEM parts after canonical validation. Filters produce separate observed outcomes.

Search clicks must refer to an actual search in the same session. Repeated/clicked outcomes can overlap. Abandonment requires a closed session and no subsequent meaningful interaction. Search and workshop funnels require ordered same-session facts. Private account→garage and unavailable scanner funnels are **not** inferred from unrelated aggregate counts.

Community reports return only counts of retained records created in the range. They include registrations (excluding anonymous guest Auth), vehicle/service/journal records, published garages, visible discussions/replies, helpful feedback, accepted answers and current unanswered technical questions. These are operational counts, not backfilled visitor events. Deletion, hiding and current reply state affect them. Private contents and individual identities are not returned.

Reports use UTC half-open ranges, at most 90 retained calendar days. Today is capped at statement time. The preceding comparison has the same number of calendar days and equal elapsed duration. Coverage periods distinguish pre-activation/paused/expired dates from actual collection. Growth percentages are withheld without complete comparable coverage or a nonzero baseline. Daily gaps remain gaps; daily browser/session counts are not added to compute period distinct totals. Content filtering applies to visitor reports, not site-wide community or commercial totals.

Financial table sorting compares integer-cent strings exactly, including values above JavaScript’s safe-integer range.

The daily rollup is a cache. Whole-period distinct counts and funnels read retained facts, never sums of daily uniques. The hourly retention/aggregation job is `e34-analytics-retention`. Reports use actual retained data; there is no demo-data branch or production QA seed.

## Privacy revision 2 — owner approval required

The website code is deployable while collection remains **disabled**. `/manage/analytics` → Collection & privacy presents the exact changes and requires an explicit checkbox before enabling. This does not reuse legacy section-count or commercial consent. Visitors then make a fresh, off-by-default choice for public-page measurements, plus separate subordinate technical-search and performance choices. Preference controls remain on `/resources#privacy`, not the public footer.

Identifiers on device expire after 30 days; event/page/session history expires after 90 days. Withdrawing permission drops queued events and stops collection. The device identifier can remain until expiry so the user can request deletion; it is not used while consent is off. The erasure endpoint cascades the current browser's visitor/session/page/event history and invalidates aggregate caches. A hashed erasure marker lasts 31 days to prevent late in-flight retries recreating erased history. Clearing browser data first loses the mapping; unidentified old observations expire under retention. Provider operational logs have their own existing policies.

Resource/rate/storage limits are deliberate: 240 events per browser/hour, 5,000/day, 100,000 retained, a database stop at 450 MiB and 10,000 erasure markers. Discarded-by-limit days are flagged as incomplete. Staff exclusion requires a signed-in identity; user-agent bot detection is heuristic, not proof of human traffic. Ad blockers, offline failures, bounded queues and consent choices create sample bias. This is not an exhaustive population or statistically validated audience estimate.

## External integrations and reports

Search Console's implemented adapter uses only E34 properties (`sc-domain:e34lore.com` or its two HTTPS prefixes), final web-search data, a date-only presence query first, bounded pagination, technical-topic normalization and public-page allowlisting. It stores real provider rows separately and records successful import range/time and caps. Query/page results are top rows; anonymized queries and omitted dates are not filled with invented zeros. Google dates are Pacific, explicitly separate from UTC visitor reports. Google sign-in OAuth is **not** reused or expanded.

**Not connected:** no Search Console credentials were created or changed. To enable the prepared sync, the owner must authorize a dedicated Google client with `https://www.googleapis.com/auth/webmasters.readonly`, enable Search Console API, grant the E34 property, and enter `GSC_CLIENT_ID`, `GSC_CLIENT_SECRET`, `GSC_REFRESH_TOKEN` into this project's Edge secrets. Never paste them into chat, Git, browser JS or public environment files. Google consent is an owner action; no World Explorer properties are queried. A manual owner/MFA sync button returns the actual missing-authorization state until configured. Indexing/search-appearance reports are not implemented by this search-analytics adapter.

Optional email setup remains explicitly deferred. Weekly/monthly **downloadable** summaries use the actual selected report. Automatic emailed reports are disabled and have no arbitrary-recipient input; sender/recipient verification and an actual scheduled-mail worker are still required before that feature can run. No reports were mailed and no Resend/SMTP secrets were touched.

No scanner is deployed, so recognition/camera/inference metrics remain unavailable. Geography, returning-member tracking, private registration→garage journeys, actual database query latency, provider hosting statistics and automatic Search Console synchronization remain open integrations. Existing synthetic HTTP/route/security tests are distinct from consented real-user performance.

## Validation and deployment

See [release verification](verification.md) for exact results and publication provenance. Tests use a disposable Unix-socket-only PostgreSQL instance, provider mocks and browser-independent client fixtures. Synthetic events never enter production. The production audit verifies installed grants, RLS, resource count, paused config, scheduled retention, no new visitors/events, and preserved historical section opens.

Operational rollback: pause collection through the administrator control (or audited administrator SQL), then roll back only the website version if needed. Keep historical tables and the ledger. Never drop the schema to roll back the UI. The old usage recorder and commercial reporting remain compatible. Recheck collection state before restoring an older website notice; old builds cannot opt visitors into revision 2.
